4.3 Hard Constraints

⚠ Constraint 1: Use uv, not pip

The project environment is managed by uv. All Python package installation must go through uv pip install, never bare pip install.

uv is significantly faster than pip (parallel resolution + download + install, cached wheels). pip is still available for reading package info but never for installing.

# ✅ Correct
uv pip install -r requirements.txt
uv pip install torch --index-url https://download.pytorch.org/whl/cu130

# ❌ Wrong
pip install -r requirements.txt
pip install torch

⚠ Constraint 2: flash-attn cannot be installed on this hardware

flash-attn does not compile on Blackwell sm_120 (CUDA 13.x). If flash-attn is detected, the vLLM start script will exit with FATAL error. The attention backend is fixed to TRITON_ATTN (pure Triton kernels, no FP8 attention kernel, avoids uncalibrated scaling factors).

# flash-attn will crash compilation on sm_120 / CUDA 13.x
# Correct attention backend for decoder models:
--attention-backend TRITON_ATTN    # ✅ Only option for this hardware

⚠ Constraint 3: CUDA 13.x + torch cu130

PyTorch must be the cu130 build (CUDA 13.0). The standard cu12x wheels are incompatible. When installing or upgrading PyTorch:

uv pip install torch --index-url https://download.pytorch.org/whl/cu130

⚠ Constraint 4: Single GPU — no tensor parallelism

There is only one GPU. All models must fit within 96 GB. Qwen3.6-27B-FP8 uses ~28 GB for model weights, ~68 GB allocated for KV cache (85% utilization). Tensor parallelism must be set to 1. No multi-node or multi-GPU distributed inference.

⚠ Constraint 5: vLLM processes are untouchable

Do not start, stop, restart, or kill any vLLM process. All Claude Code agents depend on the vLLM deployment as their LLM backend. The start script is ~/deploy/vllm-prod/start.sh and managed by systemd.

5.2 What TensorRT-LLM Would Provide

vLLM (current)

  • Pros:
  • Zero compilation — instant warm start
  • Streaming output (token-by-token)
  • PagedAttention — efficient memory for concurrent requests
  • Continuous batching — high throughput under load
  • OpenAI-compatible API out of the box
  • Dynamic shape support — no rebuild for different input sizes
  • Auto-tool-choice, reasoning-parser built in
  • Easy quantization switching (FP8, AWQ, GGUF, GPTQ)
  • Cons:
  • Uses Triton kernels — not as optimized as hand-tuned TRT engines
  • No kernel fusion across layers
  • FP8 attention kernels missing (uses generic Triton path)
  • Overhead from Python + PyTorch dispatcher

TensorRT-LLM (alternative)

  • Pros:
  • Pre-compiled TensorRT engine — hand-optimized kernels per layer
  • Full kernel fusion (attention + FFN + Layernorm)
  • FP8 weights + activations end-to-end
  • CUDA Graph support for ultra-low latency
  • PagedAttention + continuous batching (equivalent features)
  • Disaggregated serving (separate prefill/decode nodes)
  • Speculative decoding built in
  • ~15-30% throughput improvement over vLLM in benchmarked scenarios
  • Cons:
  • Build time: 30 min - 2+ hours to compile engine per model/config
  • Must rebuild for every change (batch size, context length, precision)
  • No streaming — must wait for full generation
  • Fixed shapes — engine is specific to input dimensions
  • No pip install — source build required (enroot + Docker or SLURM)
  • TensorRT backend is officially "legacy" in TRT-LLM 1.3+
  • PyTorch/AutoDeploy path still in beta

5.4 When to Choose TensorRT-LLM

Recommendation Summary

Keep vLLM if:

  • Streaming output is needed (interactive chat, agent tool calls)
  • Frequently changing context lengths or batch sizes
  • Rapid experimentation and iteration
  • Production latency targets are met by current throughput (~150 tok/s batch-8)
  • You need the AutoDeploy beta path (TRT-LLM's PyTorch-based inference)

Try TensorRT-LLM if:

  • Raw throughput is the primary metric and vLLM is a bottleneck
  • Fixed, well-defined batch sizes and context lengths
  • Benchmarking / research comparison work
  • You want to explore the PyTorch/AutoDeploy path (modern TRT-LLM direction)

Bottom line for this hardware:

On a single RTX PRO 6000 with Qwen3.6-27B-FP8, vLLM already achieves strong throughput. The ~25-30% TRT-LLM gain is meaningful for production scaling but not decisive for single-GPU inference. The 30-min-2hr engine build time, loss of streaming, and "legacy" status of the TensorRT backend make vLLM the better default. TensorRT-LLM is worth trying for benchmarking and learning (which aligns with the 30-day training plan), but not for replacing production vLLM.

5.5 The AutoDeploy Middle Path

TensorRT-LLM 1.3+ has an AutoDeploy backend (_torch/auto_deploy/) that sits between vLLM and full TensorRT compilation. It uses PyTorch + graph transforms + torch.export — no engine rebuild needed, but still gets kernel-level optimizations. This is the recommended path for TRT-LLM users who want TRT-LLM benefits without the build pain.

# AutoDeploy is the PyTorch backend — no TensorRT engine build required
# Key path: tensorrt_llm/_torch/auto_deploy/shim/ad_executor.py
# Benefits:
#   - No 30min-2hr compilation
#   - Dynamic shapes supported
#   - Kernel-level graph optimization via torch.export
#   - Still in beta, not production-ready
